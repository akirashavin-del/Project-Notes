# 2. REQUIRED TECHNOLOGY

Use this architecture unless there is a strong technical reason to change it.

## Frontend

Use:

* React
* Vite
* JavaScript or TypeScript
* Modern CSS
* Responsive design

The frontend MUST run with:

```bash
npm run dev
```

and production build with:

```bash
npm run build
```

Create a proper:

```text
package.json
```

with all required dependencies and scripts.

# 3. BACKEND

Use:

* Python
* FastAPI
* Pydantic
* Uvicorn

The backend MUST run with:

```bash
uvicorn main:app --reload
```

or provide:

```bash
python main.py
```

if appropriate.

Create a clean backend structure such as:

```text
backend/
│
├── main.py
├── requirements.txt
├── .env.example
│
├── api/
├── models/
├── schemas/
├── services/
├── database/
└── utils/
```

Do NOT put the entire backend into one huge file.

# 5. APPLICATION REQUIREMENTS

The application must contain real functionality.

Every important button must do something.

Every form must:

1. Accept user input
2. Validate the input
3. Send the appropriate request
4. Handle loading state
5. Handle success
6. Handle errors
7. Update the UI

Do NOT create fake buttons such as:

```text
Coming Soon
```

unless the feature genuinely cannot be implemented.

Do NOT use fake API responses when a real backend implementation is possible.

---

# 6. FRONTEND ↔ BACKEND

Connect the React frontend to FastAPI.

Use REST APIs unless another protocol is clearly required.

Example:

```text
React
   ↓
HTTP Request
   ↓
FastAPI
   ↓
Service Layer
   ↓
Database / AI / External API
   ↓
FastAPI Response
   ↓
React UI
```

Create a centralized API service.

For example:

```text
src/services/api.js
```

Do not scatter API URLs throughout components.

Use an environment variable such as:

```env
VITE_API_URL=http://localhost:8000
```

Backend:

```env
PORT=8000
```

---

# 7. API DESIGN

Create proper API endpoints based on the project.

For example:

```text
GET    /api/health
GET    /api/items
GET    /api/items/{id}
POST   /api/items
PUT    /api/items/{id}
DELETE /api/items/{id}
```

Adapt these endpoints to the actual project.

Every endpoint should:

* Validate input
* Return appropriate HTTP status codes
* Return structured JSON
* Handle exceptions
* Avoid leaking sensitive information

Also provide:

```text
GET /docs
```

through FastAPI's automatic Swagger documentation.

# 8. DATABASE

If the project needs persistent data, implement a real database.

Preferred options:

* PostgreSQL for production
* SQLite for simple local development

Use an ORM or clean database abstraction.

Create:

```text
database/
├── connection.py
├── models.py
└── repository.py
```

Do not store important application data only in frontend state.

Create appropriate tables based on the project.

For example:

```text
users
projects
records
results
events
```

Adapt the schema to the actual application.

# 9. AUTHENTICATION

If the project requires user accounts, implement proper authentication.

Include:

* Registration
* Login
* Logout
* Password hashing
* Protected API routes
* User sessions or JWT
* Frontend authentication state

Never store plaintext passwords.

Never expose secrets in frontend code.

Create:

```env
SECRET_KEY=
DATABASE_URL=
```

inside `.env.example`.

---

# 10. AI / ML INTEGRATION

If the project requires AI:

DO NOT put API keys directly into React.

Correct architecture:

```text
React
   ↓
FastAPI
   ↓
AI Service
   ↓
LLM / ML Model / External AI API
   ↓
FastAPI
   ↓
React
```

Use environment variables:

```env
AI_API_KEY=
```

The frontend must never receive the secret API key.

Create a dedicated AI service such as:

```text
backend/services/ai_service.py
```

The AI functionality should be actually connected to the application.

# IMPORTANT DEVELOPMENT RULE

Do not assume the project is a generic CRUD application.

Understand the PROJECT IDEA first.

Build the UI, backend, database, AI and APIs specifically around the project's real purpose.

The final application should feel like a real product built for the stated users — not a template with the project name changed.

If a requirement is ambiguous, choose the simplest reasonable implementation and continue rather than stopping unnecessarily.

The priority is:

FUNCTIONALITY > SIMPLICITY > RELIABILITY > VISUAL POLISH > COMPLEXITY.
